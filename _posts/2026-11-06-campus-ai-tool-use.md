「系统里现在有多少篇文章？」

这个问题塞给 RAG 是答不对的。向量库能召回「和文章统计有关的段落」，但答案是 `count(*)`，不是任何一段文字。只要问题的答案在数据库里、是**可通过查询确定**的，就不该走检索——检索给你的是相似，SQL 给你的是准确。

智慧校园平台的 AI 助手走的是另一条路：不做向量库，直接给模型六个函数，让它自己查。

## 六个工具，全是只读

| 工具                       | 参数             | 覆盖的问法               |
| -------------------------- | ---------------- | ------------------------ |
| `get_article_count`        | 无               | 「一共多少篇」           |
| `get_recent_articles`      | `days`（默认 7） | 「最近有什么新文章」     |
| `get_pending_articles`     | 无               | 「有哪些待审核」         |
| `search_articles_by_title` | `keyword`        | 「找一下标题带 XX 的」   |
| `get_article_by_id`        | `id`             | 「这封文章讲了什么」     |
| `get_article_stats`        | 无               | 「发布/草稿/删除各多少」 |

这套切法不是按数据库表切的，是按**问法**切的：多少 / 最近 / 待办 / 找 / 看详情 / 概览。六个入口覆盖后台运营人员真实的六类提问，粒度刚好——再细，模型选工具的错误率上升；再粗，一个工具塞太多分支，参数就得靠模型猜。

**全部只读，是设计选择不是能力不足。** 一个能调 `delete_article` 的模型，迟早会在你说「把这篇删了」的时候删错一篇。删一篇的代价远高于答错十次：答错可以重问，删错要去数据库里捞。所以 system prompt 里写死两条：

> - 只能使用**只读**工具，不能执行新增、修改、删除、发布等写操作
> - 当用户请求写操作时，明确拒绝并说明当前助手只支持只读查询

写操作该由人来点按钮。模型最多帮你把参数填好，**但不能替你按下确认**。

## 工具循环是手写的，只有三轮

没有用框架，就是一个 for 循环：

```java
for (int i = 0; i < MAX_TOOL_ROUNDS; i++) {          // MAX_TOOL_ROUNDS = 3
    OllamaChatResult r = ollamaClient.chat(workingMessages, toolDispatcher.getToolSchema());
    if (r.getToolCalls() == null || r.getToolCalls().isEmpty()) {
        return finish(r.getContent());               // 没有工具调用 = 收工
    }
    // 1. 把带 tool_calls 的 assistant 消息压回上下文
    // 2. 逐个执行，每个结果作为 role=tool 的消息压回上下文
    // 3. 继续下一轮
}
```

三个设计点：

**上限三轮。** 不是怕死循环，是怕**死循环还烧钱**。本地 Ollama 不要钱，但如果是按 token 计费的模型，一个反复调同一个工具的循环能在几分钟里烧掉一天预算。三轮足够覆盖「先搜标题、再按 id 看详情」这种两步操作，再多就说明提示词或工具描述有问题了。

**工具失败不抛异常，当作上下文回填。** 执行器把所有异常都吞成 `success=false` + 错误信息，然后照常塞进 `role=tool` 消息：

```java
try {
    toolResult = toolDispatcher.execute(toolCall.getName(), toolCall.getArguments());
} catch (Exception ex) {
    toolResult.setSuccess(false);
    toolResult.setSummary(ex.getMessage());
}
```

这样模型能看见「这个 id 不存在」，然后自己换一种方式再查，或者老实说没找到。抛 500 只会让用户看到一个白屏。

**模型空回复时用工具摘要兜底。** 小模型（llama3 这个量级）有时候调完工具就沉默了。`fallbackAssistantContent` 的处理是：模型没说话，就拿最后一条工具结果的 summary 顶上去——那条 summary 本来就是给人看的 Markdown。

## 引用溯源：能做到哪一步

这是这个模块最值得说、也最容易被说大的部分。

工具执行完会把命中的对象塞进 `ReferenceItem(type, id, title)`，服务层按 `type:id` 去重合并，随响应一起返回：

```java
LinkedHashMap<String, ReferenceItem> map = new LinkedHashMap<>();
toolResults.stream()
    .flatMap(t -> t.getReferences().stream())
    .forEach(ref -> map.putIfAbsent(ref.getType() + ":" + ref.getId(), ref));
```

前端拿到的是一个可点回原文的列表。用户问「最近的文章」，回答下面挂着那几篇文章的标题，点一下跳过去。

**但要说清楚它是什么：引用是指针，不是证据。**

`ReferenceItem` 只有 `type / id / title` 三个字段，没有片段，没有位置，没有引用编号。模型在正文里也不会写 `[1]` `[2]`。所以「回答强制带引用」严格来说等于「响应必带引用列表」——它保证用户能一键回到数据源，但**不保证正文里每一句都能对上某一条引用**。

更要命的是，聚合类工具（`get_article_count`、`get_article_stats`）返回的引用是空列表——因为「一共 128 篇」这句话没有可指向的对象。这是引用机制的天然边界：**指得回去的才叫引用，指不回去的只能靠回答本身说得像人话。**

真要走到「每句话可核验」，得两步：让模型输出带角标，服务端解析角标并校验角标编号落在 references 范围内；校验不过就把答案打回重答。这一步没做，是这套实现目前的短板，也是下一步的入口。

## 上下文：十二条消息，加一份页面上下文

会话存在 `ConcurrentHashMap<String, List<AiConversationMessage>>` 里，滑动窗口 12 条，超了从头砍。

够用，也够粗糙。三个已知问题：

1. **重启即失忆。** 内存存消息，进程一挂会话全丢。真要上生产得换 Redis，但那样就得处理序列化和过期。
2. **砍的是最早的消息，不是最没用的消息。** 用户第一轮说的「我在管文章后台」这种设定，第 13 轮就被砍掉了。
3. **没有摘要。** 12 轮之后模型对前面发生的事一无所知，用户得重新说一遍。

补救的办法是 `pageContext`：每次请求带上当前页面信息，序列化进 system prompt。用户在文章详情页问「这篇文章呢」，模型知道「这篇」指谁——**这个指代不是靠记忆解决的，是靠每次重新告诉它。**

对后台助手来说这个取舍是对的：用户在同一页面上连续问的问题高度相关，页面上下文比历史消息更能锚定「现在在说哪个对象」。

## 三个坑

**文档和实现漂移。** README 的工具表写 `get_recent_articles` 参数是 `limit`，代码里是 `days`；`get_pending_articles` 文档写支持 `limit`，实现里硬编码了 100。小项目里这种漂移很常见，但工具描述是**直接喂给模型**的——描述错了，模型就按错的方式调用，然后你会在日志里看到一堆参数解析异常。

**小模型乱调工具。** llama3 这个量级在「用户闲聊时也硬要调一个工具」这件事上很固执。缓解办法是工具描述写得足够具体（「按标题关键词搜索，不要用于全文检索」），以及接受一定比例的误调用——它不是 bug，是当前模型能力的价格。

**没有任何评估。** 这套东西到现在不知道准确率是多少。没有评估集，就没有「改了提示词之后变好了还是变坏了」的判断依据，只有「我感觉好像强了点」。这是最该补的一块。

## 什么时候该用哪条路

一句话的分界：

- 答案在**文档**里、需要语义匹配 → 检索（RAG）
- 答案在**数据库**里、可以用查询确定 → 工具调用（Tool Use）
- 两者都有 → 让模型自己选：知识库检索和业务工具都注册成工具，ReAct 循环里它自己决定查哪个

这套校园平台属于第二种，所以它一个向量库都没有。不是因为向量库不好，是因为**这里的问题不需要相似，需要准确**。
