RAG 的 demo 和平台，分界线不在模型。

demo 只需要回答「能不能答出来」。平台要回答的是另一个问题：**答错了，是入库那一步切坏了，还是召回没捞到，还是模型自己编的？** 这个问题不解决，迭代就只能靠换模型碰运气。

拿 Ragent 当样本拆一遍。它做了三件事，各自解决一个不同层面的问题：七个 Maven 模块解决依赖方向，一条 JSON 描述的入库流水线解决可定位，四路并行召回解决覆盖率。

## 七个模块，但不是微服务

| 模块         | 职责                                                                                 | 关键约束                  |
| ------------ | ------------------------------------------------------------------------------------ | ------------------------- |
| `framework`  | 统一响应与异常、幂等、分布式 ID、MQ 适配、SSE、跨节点流式取消                        | 不认识任何业务            |
| `infra-ai`   | Chat / Embedding / Rerank / VLM 客户端，模型档位、路由、首包探测、健康状态、熔断降级 | 不认识 rag 和 agent       |
| `system`     | 用户认证、审计日志                                                                   | 位于各业务引擎之下        |
| `rag`        | 问答、知识库、入库 Pipeline、意图树、检索、会话、管理端 API                          | 依赖上面三个              |
| `agent`      | AgentScope ReAct 执行引擎，接知识检索与 MCP 工具，支持技能、记忆、人工确认           | 唯一装配 MCP 客户端的地方 |
| `bootstrap`  | 启动装配                                                                             | 只有启动类和主配置        |
| `mcp-server` | 独立的 MCP 工具示例服务（天气、票务、销售、联网搜索）                                | 独立进程                  |

分层本身不稀奇，值钱的是**依赖方向单向**：`bootstrap` → `rag`/`agent` → `system`/`infra-ai` → `framework`。换个向量库、换家模型供应商，改的是最底层的实现类和配置，`rag` 里的问答主流程一行不动。

那为什么不拆成微服务？因为一次提问要穿过 `rag` 的检索、`agent` 的工具调用、`infra-ai` 的模型路由。拆开就是三次跨进程调用加三份链路追踪，而这三部分的**变更频率是一样的**——它们本来就是一起改的。模块边界该切在变更频率不同的地方，不是切在名词不同的地方。

这也是模块化单体的正确用法：先在编译期把边界钉死（模块之间不能随便 import），等某一块真的需要独立扩容了，再拿出去。

## 入库：流水线是数据，不是代码

这是整个项目里最值得抄的部分。

大多数 RAG 项目的入库是一段写死的 `main`：读文件、切分、调 embedding、写库。加一个「先让 LLM 修一下 PDF 排版」的需求，就得改代码、重新发版。

Ragent 把入库做成了一条由 JSON 描述的节点链：

```json
{
  "name": "pdf-ingestion-pipeline",
  "nodes": [
    { "nodeId": "fetcher-1",  "nodeType": "fetcher",  "nextNodeId": "parser-1" },
    { "nodeId": "parser-1",   "nodeType": "parser",   "settings": { "rules": [{ "mimeType": "PDF" }] }, "nextNodeId": "enhancer-1" },
    { "nodeId": "enhancer-1", "nodeType": "enhancer", "settings": { "modelId": "qwen-plus", "tasks": [...] }, "nextNodeId": "chunker-1" },
    { "nodeId": "chunker-1",  "nodeType": "chunker",  "settings": { "strategy": "fixed_size", "chunkSize": 512, "overlapSize": 128 }, "nextNodeId": "indexer-1" },
    { "nodeId": "indexer-1",  "nodeType": "indexer",  "settings": { "embeddingModel": "qwen-emb-8b", "includeEnhancedContent": true, "metadataFields": ["category", "department"] } }
  ]
}
```

三段式：`nodeId` 是身份，`nodeType` 指向注册表里的一个实现，`settings` 是类型各自的配置。执行引擎只认 `nextNodeId`，不认具体类型——所以新增一个节点，是「实现 `IngestionNode` 接口 + 注册成 Spring Bean + 在 JSON 里写一行」，不是改引擎。

好处直接体现在排障上：一条文档处理失败，日志能告诉你死在第几个节点、那个节点的入参是什么。写死的脚本只能给你一个异常栈。

## enhancer 那个节点的提示词，值得单独看

`enhancer` 用 LLM 修 PDF 解析出来的烂排版——断行、页眉页脚、表格被打散。它在 prompt 里把边界钉得很死：

> **最高原则：任何内容不得被改写、删减、补充、纠错、润色、同义替换或重排语义。只能修复格式，不得改变信息本身。**
>
> - 所有汉字/标点/数字/英文/单位/日期/专有名词必须与原文完全一致（逐字符一致）。
> - 若遇到无法确定的结构问题，宁可保留原样也不要猜。

这是把 LLM 放进 ETL 的正确姿势：**它只被允许做「不确定但可验证」的那部分工作，且被明确禁止做任何需要判断的事。**

同样一条原则反过来说：凡是要它「顺手改一下错别字」的，都会污染召回——原文写错了，用户搜的就是错的那个词，你把它改成对的，反而搜不到了。

## 四路召回：每加一路都在加成本

向量、关键词（BM25）、知识图谱、联网搜索，四路并行，然后去重、RRF 融合、Rerank。

每一路补的是另一路的洞：

| 通道     | 补什么洞                               | 代价                                       |
| -------- | -------------------------------------- | ------------------------------------------ |
| 向量     | 同义、跨表述的语义匹配                 | 代码标识符、错误码、版本号这类字面量匹配差 |
| BM25     | 精确串匹配                             | 不懂同义词，搜「幂等」捞不到「防重复提交」 |
| 知识图谱 | 实体之间的关系（谁属于谁、谁引用了谁） | 要预先建图，抽取质量决定天花板             |
| 联网搜索 | 知识库外的时效信息                     | 结果不可控，必须标注来源否则无法追责       |

前两路是标配，我在[上一篇]({% post_url 2026-10-24-rag-hybrid-recall-rrf %})里推导过 RRF 为什么只比名次不比分数——两路的分数不在一个量纲上（余弦 0~1，BM25 无上界），加权求和要先归一化，而归一化参数得跟着查询调，等于拍脑袋。

四路的代价是**延迟取 max**，不是取和。只要有一路慢，整条召回就被拖住。所以工程上真正的工作量不在「接第四路」，而在超时预算怎么切：每一路给一个 deadline，到点就按已返回的算，融合层对缺席的通道不做惩罚。

融合之后还有一层排序：40 条进 Rerank，出 10 条喂给模型。RRF 只解决「怎么公平地合并两份名单」，没解决「相关性到底谁高」——cross-encoder 把查询和段落一起编码，判断质量高得多，但也慢得多，所以只能用在四十条这个量级上。

## 模型层：把供应商差异关进 `infra-ai`

`infra-ai` 里定义了 `ChatClient` / `EmbeddingClient` / `RerankClient` 三个接口，上层只认接口。换供应商，是实现类加配置的事。

它额外做了三件在国内环境里必须做的事：

1. **模型档位**：同一能力配多个候选，按价格/质量分档，故障时往下掉一档而不是直接失败。
2. **首包探测**：流式接口真正的健康度不是 HTTP 200，是第一个 token 多久回来。只测连通性，等于没测。
3. **熔断降级**：连续失败到阈值就摘掉这个候选，隔一段时间放一个探测请求试探恢复。

这三件事如果散在业务代码里，每接一个新供应商就要重写一遍。收在一个模块里，业务侧只看到「调用了 ChatClient，成功了」。

## 这套结构的边界

模块化单体的天花板很明确：**所有模块共享一个 JVM 堆**。`rag` 里一次大文档的解析会把整个服务的 GC 拖下水。真到那一天，第一个该拆出去的就是入库——它是唯一「CPU 密集 + 长任务 + 可异步」的部分，拆出去代价最小、收益最大。

四路召回也不是越多越好。知识图谱的前提是实体抽取质量，抽不准的图谱比没有图谱更糟——它会稳定地把错误答案排到前面，而且你还看不出问题出在图谱。什么时候该退回两路：**当你没法评估第三路带来的增益时。**

Rerank 同理，它把召回的所有误差放大成一个看起来很有把握的排序结果。没有评估集的时候加 Rerank，是在给自己制造虚假的安全感。

---

这套项目最值得学的不是某个算法。是它把「一条文档怎么进来」和「一个问题怎么被回答」都做成了**可观测、可回放、可局部替换**的链路。RAG 做到最后，拼的不是模型，是这条链路上每一个环节你敢不敢单独换掉。
