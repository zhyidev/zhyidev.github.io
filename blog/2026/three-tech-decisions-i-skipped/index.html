两个我最终没用的技术：Seata 与 ES 官方客户端

Created on November 04, 2026

2026   ·   技术选型   架构   后端   ·   后端

前面的文章讲了我用了什么。这篇讲我没用什么。

技术选型里最难的不是「选什么」——候选方案就那么几个，查文档都能查明白。难的是「敢不选什么」：当着评审的面说「这个我们不引入」，比说「这个我们也上了」要难得多。

三个减法，三个理由。

一、没用 Seata：因为这条链路不需要「原子」，只需要「收敛」

跨三个服务、四张表，第一反应当然是上分布式事务。我认真看过 Seata 的 AT 模式，最后没用。

AT 模式的成本：每个参与方要建 undo_log 表、要接全局锁、要多部署一个 TC 协调者并保证它高可用。这三件事都是运维负担，而且 TC 本身变成了新的单点。

更关键的是需求判断：电商场景真的需要「要么全成功、要么全失败」吗？

不需要。「订单待支付、库存已占」是完全正常的中间态——用户看得见，客服解释得清，超时任务会回收。硬把它做成原子的，是在为一个不存在的需求付成本。

所以最终方案是：本地事务 + 本地消息表 + 消费幂等 + 对账兜底。代价是中间态会对外可见，而这一点在电商里本来就是业务语义的一部分。

判断标准其实很简单：你的业务能不能容忍「中间态被看见」。能，就别上 2PC；不能（比如转账），才需要。

二、没用 ES 官方客户端：因为只用两个端点

Elasticsearch 的 Java 客户端有一个特点：版本必须和服务端对齐。8.x 的客户端连 7.x 的集群会直接不兼容。

而我只用了两个端点：

POST /{index}/_search      # 查询
PUT  /{index}/_doc/{id}    # 写入

为这两个端点引入一个几十 MB、且跟服务端版本强耦合的客户端，性价比很低。所以直接用 Spring 的 RestClient 裸调 HTTP：

Map<?, ?> body = elastic.post()
    .uri("/" + alias + "/_search")
    .body(Map.of("size", limit * 2, "query", Map.of("bool", ...)))
    .retrieve()
    .body(Map.class);

换来的是：升级 ES 集群不用动一行代码，只要 JSON 形状不变。 代价是：一旦要做 bulk 批量索引、scroll 深分页、复杂聚合，手写 JSON 会开始痛苦。到那天再引客户端，也只需要换掉一个工厂类。

三、没用 Redis 预扣库存：因为会把一个问题变成两个

「高并发扣库存用 Redis 预扣」几乎是标准答案。我没用。

原因是：Redis 和 MySQL 之间仍然要一致。预扣成功但落库失败怎么办？就得再写一套补偿去回滚 Redis。于是「MySQL 单库内的一致性问题」变成了「Redis + MySQL 跨系统的一致性问题」——问题的数量翻倍了。

而我的实际量级是：QPS 不高、冲突集中在同一 SKU 的少量行上。用一条带条件的 UPDATE 就够了：

UPDATE inventory_stock
   SET available_quantity = available_quantity - ?,
       locked_quantity    = locked_quantity + ?,
       version            = version + 1
 WHERE sku_id = ? AND available_quantity >= ?

影响行数 ≠ 1 就是库存不足，直接报冲突。判断和修改在同一条语句里，没有窗口。

这条经验值得记住：每一个为了「性能」引入的缓存/中间层，都会带来一个新的不一致面。先证明确实扛不住，再引。

四、代价

三个减法不是没有成本，诚实列出来：

  1. 没有全局一致性保证：靠人肉补偿，而补偿会漏。比如「释放库存」失败时如果吞掉异常，这段库存就滞留到过期回收，期间可售量被虚减，且日志里没有痕迹。正确做法是落补偿失败表 + 告警。
  2. 手写 HTTP 意味着没有类型安全：ES 的查询 DSL 是 Map 拼出来的，字段名写错要到运行时才报。这和手写 SQL 是同一类问题。
  3. 拒绝 Redis 预扣的前提是量级小：如果真到了单 SKU 每秒上千次扣减，MySQL 行锁会成为瓶颈，那时必须回头做预扣 + 异步落库，并且认真设计对账。

一句话：「不用」比「用」更需要理由，因为「不用」意味着你要自己承担它本来能解决的问题。
